\begin{abstract}
This proposal outlines the engineering implementation of a privacy-preserving messaging platform that decouples message integrity from identity revelation. Leveraging Yubikey hardware PRF and nested Ring Signatures, the system allows users to send undeniable, tamper-proof messages anonymously, with the exclusive capability to retroactively prove authorship. The project adopts an Agile methodology, utilizing React/TypeScript for the frontend and Node.js for the backend.
\end{abstract}

\section{Executive Summary and Highlights}

\subsection{Overview}
Project AIVS (Anonymous Identification Verification System) is a cryptographic engineering initiative designed to solve the paradox in secure communications: the trade-off between anonymity and accountability, and introducing a hardware smartcard to participate in this process to ensure the security of the private keys.
\subsection{Key Highlights}
\begin{itemize}
    \item \textbf{Hardware Security:} Utilizes Yubikey PRF to generate unpredictable passphrases, ensuring keys never leave the hardware boundary.
    \item \textbf{Nested Ring Signatures:} Employs a dual-layer signing mechanism (Inner Ring for identity proof, Outer Ring for anonymous transmission) to ensure mathematical unlinkability.
    \item \textbf{Selective Disclosure:} Grants the sender full control over identity revelation. No central authority can unmask the user; only the holder of the physical hardware token can decrypt the proof.
    \item \textbf{Agile Engineering Stack:} Built on a modern, type-safe stack (React + TypeScript + Node.js) designed for auditability and rapid iteration.
\end{itemize}

\section{Problem Motivation}

\subsection{Problem Statement}
In modern digital communication, there is always a trade-off between authenticity and anonymity. As more and more users are concerned about surveillance and data breaches, a system that can protect user identity becomes more and more important. In the meanwhile, verifiability and accountability of message are still crucial factors for the trustworthiness of the digital communication.

However, most of the existing solutions tend to compromise one side over the other instead of addressing both at the same time. 

OpenPGP or S/MIME are examples of Public Key Infrastructure (PKI), where digital signatures are tied to a long-term identity. This mechanism ensures the verifiability of the original message and non-repudiation, but it also limits anonymity as every signed message can be traced back to the user. This demonstrates a typical trade-off between authenticity and anonymity in the real-world scenario.

In terms of anonymous communication systems, those Tor–based systems are designed to hide user identity. These systems focus effectively on a privacy perspective, but they also introduce the difficulty of verification for the authorized message sender as there is no sign of identity. This increases the risk of impersonation and Sybil attacks, and it also prevents users from later proving authorship when needed. This limitation is essential to be addressed under scenarios like whistleblowing or dispute resolution, where both anonymity and credibility are required.

Another problem related to key management is that private keys are still handled in software in many cryptographic schemes, including those designed for anonymity like ring signatures. This deficit significantly compromises the system and makes it exposed to common attack vectors such as memory inspection or malware.

Overall, these existing schemas suggest the need for a solution that can fully ensure both privacy and accountability. To address this gap, a mechanism that allows messages to remain unlinkable by default, while still giving the original sender the ability to reveal authorship later in a controlled and verifiable way, without relying on a third party, is introduced in this project.

\subsection{Objectives}
The main goal of this project is to design a system that separates the act of signing a message from the act of revealing identity, while still maintaining both security and practical usability. 

To guide the design, the following objectives are defined:

\begin{itemize}[label=\textbf{Objective \Alph*:}]
    \item \textbf{Hardware-Isolated Key Derivation} \\
    The system uses the WebAuthn PRF extension to derive one-time signing keys ($OTK$) with the help of a hardware security device. By doing so, sensitive key material does not leave the hardware boundary, which helps reduce the risk of key exposure even if the host environment is not fully trusted.
    
    \item \textbf{Nested Ring Signature Construction} \\
    A two-layer ring signature scheme is introduced using a 1-of-$N$ structure (with $N = 8$). This allows a message to be verified as valid while keeping the actual signer indistinguishable from other members of the group.
    
    \item \textbf{Selective Disclosure Mechanism} \\
    The system supports a challenge-response process that allows the original sender to prove authorship when necessary. This is achieved through an encrypted proof ($Sig_{inner}$), which can only be accessed using a hardware-derived secret. As a result, identity disclosure remains entirely under the control of the sender.
    
    \item \textbf{Practical Performance} \\
    Since the system is intended for use in a browser environment, performance is also taken into account. In the meanwhile, a non-delay user interaction is guaranteed by keeping cryptographic operations efficient.
\end{itemize}

\section{System Overview and Workflow}

\subsection{System Roles and Trust Assumptions}
The system involves three primary roles: the Sender, the Recipient, and a Backend Server, with a YubiKey hardware token participating in cryptographic operations. Both the Sender and the Recipient interact with the system through a web browser, while the backend server functions solely as a message relay and storage service.

All cryptographic operations are performed locally on the client side with the assistance of the YubiKey. The server does not generate, store, or process private keys, and only handles opaque data blobs, including messages, signatures, and encrypted proofs. The YubiKey is used to provide hardware-bound PRF outputs that participate in one-time key derivation and proof encryption, without exposing secret material to the browser or operating system.

The system does not maintain a global signing key registry. Each message is associated with a freshly derived one-time key, and no signing keys are reused across messages.

\subsection{Workflow}
The workflow consists of an anonymous message transmission phase followed by an optional identity verification phase.

During message transmission, the Sender composes a message using a browser-based client with a connected YubiKey. A one-time key is derived with the participation of the YubiKey and used, together with a fixed set of randomly generated decoy keys, to construct a ring signature over the message. To support future authorship verification, an additional inner ring signature is generated and encrypted as a proof using a symmetric key derived from the YubiKey PRF output. An outer ring signature is then computed over the message concatenated with the hash of the encrypted proof. The message, outer signature, and encrypted proof are transmitted to the Recipient via the backend server.

Upon receipt, the Recipient verifies the outer ring signature to confirm message integrity and authenticity, while the Sender’s identity remains hidden within the anonymity set. The encrypted proof is not required for this initial verification.

If identity verification is later requested, the Recipient sends the original message, signature, and encrypted proof to the claimed Sender. Using the same YubiKey, the Sender derives the corresponding decryption key and decrypts the proof to reveal the inner ring signature. The decrypted signature is returned to the Recipient, who verifies its validity and linkability against the original message and signature to confirm authorship.


\section{Methodology and Technical Design}

\subsection{Security Model}
\begin{itemize}
    \item \textbf{Key Derivation:} The OTK is derived with the participation of the Yubikey, ensuring it cannot be predicted or extracted.
    \item \textbf{Anonymity Set:} 1 real signer + 7 random decoys = 8 total keys. Probability of guessing the signer is $1/8$ per message (statistically negligible for identification).
    \item \textbf{Forward Secrecy:} Compromise of the Yubikey allows decryption of past Proofs but does not reveal the identity of past messages \textit{unless} the attacker actively performs the decryption and linking.
\end{itemize}

\subsection{Technical Stack Chosen}
\begin{itemize}
    \item \textbf{Frontend:} React, TypeScript.
    \item \textbf{Cryptography (Client):} WebAuthn API (PRF extension), Elliptic Curve Library (e.g., \texttt{elliptic} or WASM-based Rust bindings) for Ring Signatures.
    \item \textbf{Backend:} Node.js (Express/NestJS).
    \item \textbf{Database:} PostgreSQL(Stores only blobs: Message, Public Keys Ring, Signature, Encrypted Proof).
\end{itemize}

\subsection{Cryptographic Construction}
\begin{enumerate}
    \item \textbf{Setup:} Generate One-Time Key ($OTK$) via Yubikey. Generate 7 Fake Keys ($FK_{1...7}$).
    \item \textbf{Inner Layer (The Proof):}
    $$ Sig_{inner} = RingSign(Message, \{OTK, FK_{1...7}\}) $$
    $$ Key_{proof} = KDF(PRF_{Yubikey}(Hash(OTK))) $$
    $$ Proof = Encrypt_{AES-GCM}(Sig_{inner}, Key_{proof}) $$
    where the hash of the $OTK$ is used as a salt to bind the proof key to the one-time signing key.
    \item \textbf{Outer Layer (The Transmission):}
    $$ Sig_{outer} = RingSign(Message || Hash(Sig_{inner}), \{OTK, FK_{1...7}\}) $$
    \item \textbf{Verification:} Upon decryption, the Linkable Tag of $Sig_{inner}$ must equal the Linkable Tag of $Sig_{outer}$.
\end{enumerate}

\section{System Design}

\subsection{Architecture Overview}
The system follows a \textbf{Thick Client, Thin Server} architecture. The server acts purely as a bulletin board and relay, possessing zero knowledge of user identities or private keys, and is explicitly excluded from the trusted computing base.

\subsection{Component Diagram}
\begin{verbatim}
[Client A (Sender)]          [Server (Node.js)]          [Client B (Recipient)]
       |                            |                            |
   (Yubikey)                        |                            |
       | -- Gen OTK & Sig -->       |                            |
       | -- POST Message --->       |                            |
       |                            | -- Store Message -->       |
       |                            |                            |
       |                            | -- WS / Push Event -->     |
       |                            |                            |
       |                            |             (Verify Outer Sig locally)
       |                            |                            |
   (Challenge) <------------------  | <----- Request Proof ----- |
       |                            |                            |
   (Decrypt Proof)                  |                            |
       | -- Send Decrypted Sig ->   |                            |
       |                            | -- Forward Sig ----------> |
       |                            |                            |
       |                            |             (Verify Inner Sig & Link)
\end{verbatim}

\subsection{Data Flow}
\begin{enumerate}
    \item \textbf{Registration:} None required for the messaging protocol itself (stateless). Optional username registration maps public handles to WebAuthn Credential IDs for routing.
    \item \textbf{Signing:} All cryptographic operations occur in the browser memory. The Yubikey is accessed via `navigator.credentials.get({ prf: ... })`.
\end{enumerate}
